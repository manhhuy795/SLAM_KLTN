## Source and schema

- `web/backend/app/services/agv_station_graph.py`: supplied, versioned graph validation and Dijkstra; no physical edges bundled. `agv_mission_adapter.py`: LINE-only task boundary, graph/source validation, durable pickup/delivery/return intents, mock transport injection and Task transitions. The production singleton has **no graph provider or transport**, so `WRMS_AGV_AUTO_DISPATCH_ENABLED=1` alone still fails closed.
- `models/agv_mission.py` adds `agv_missions` and `agv_mission_commands`. Mission owns one Task, robot, selected map, graph version, optional verified PICKUP handoff and a nullable active slot. A unique `(robot_id, active_slot)` constraint permits one active mission per robot; unique `(mission_id, mission_stage)` and `(robot_id, command_sequence)` constrain stage duplication and sequence reuse. Commands persist UUID, route/target/marker, status, timestamps, claim, cancellation, arrival/stopped evidence and failure details. DB compare-and-set claims a command before mock send; a duplicate claim does not resend. SQLite file-backed tests cover concurrent claims, but this is **not exactly-once physical execution**.
- `models/agv_cargo_evidence.py` adds `agv_cargo_evidence` keyed by capture ID. It records task, robot, delivery command, station, image reference, presence result, confidence, provenance and review status. `services/agv_cargo_verifier.py` requires matching ARRIVED delivery command with stopped evidence, validates capture time and identity, and makes repeated identical capture submissions idempotent. Shape classification is separate; PRESENT blocks manual delivery proof, ABSENT/UNCERTAIN require manual review. `WRMS_AGV_CAMERA_AUTO_CONFIRM_ENABLED` defaults off; production has no analyzer and no automatic proof mutation.
- `init_db.py` imports the new models; `app/main.py` creates the three tables with `checkfirst=True` after existing tables. These are additive table creations, not changes to existing rows or constraints. Existing databases should be backed up before upgrade. **Rollback:** turn both new flags off and revert the Phase 3C source while retaining the new tables/data; dropping tables would destroy mission evidence and is not part of safe rollback. No versioned migration or destructive migration was run.

## Ownership, execution and recovery

`claim_mission` validates `Task.robot_id`, active LINE robot, selected saved map and graph version. Command creation is stage-idempotent; one unresolved command blocks the next stage. REQUESTED → ACCEPTED → ACKNOWLEDGED → EXECUTING are distinct. Correlated ARRIVED additionally requires matching task/robot/command/sequence/target/marker, verified physical marker, stopped state and an ordered timestamp. ACK, distance, timeout or disconnect cannot produce arrival or Task completion. Uncertainty keeps the robot slot claimed; retry is not automatic. Cancellation blocks later stages and needs correlated stopped evidence before terminal cancellation. Stopped evidence checks task/robot/command/sequence, an explicit `stopped_verified` signal and post-cancel time; a verified midroute stop does not require target-station arrival. This is a mock contract, not a verified firmware signal. A completed delivery Task can cancel a stuck return command without undoing delivery. Return to PICKUP can hand off to the next valid waiting LINE Task only after verified return arrival; otherwise return HOME.

`recover_unresolved_commands` is an **explicit offline reconciliation function**: stop all backend workers first, then quarantine pending commands as UNKNOWN and inspect the physical robot before any retry. It is deliberately not run at every worker startup, because that could mark a live worker's command uncertain. There is no shared lease/leader or safe online recovery entry point yet. A backend restart never blindly resends commands; pending durable claims block new stages until coordinated reconciliation. Do not present this as production-grade multiworker recovery.

## API and event compatibility

- Existing AMR TaskExecutor/Nav2 paths and payloads remain. LINE start, proof and cancellation branch to the AGV adapter; default production LINE start still returns the existing 409 detail. Manual LINE status PATCH and generic task-command ACK cannot bypass AGV mission evidence. Manual AGV telemetry and M1–M4 endpoints retain their behavior and separate `WRMS_AGV_ENABLE_COMMANDS` flag.
- New `POST /api/agv/{robot_code}/mission-events` accepts command-correlated ACKNOWLEDGED, EXECUTING, ARRIVED and STOPPED events only with the existing device token, matching LINE robot, default-off AGV dispatch flag and configured adapter. The production adapter is unconfigured, so the endpoint remains inert. Accepted ARRIVED/STOPPED callbacks reuse existing `EVENT_CREATED` and `TASK_UPDATED` WebSocket shapes. No real firmware currently sends this payload; device authentication and evidence semantics require hardware validation before use.
- Existing Task creation still derives pickup from `Product.default_rack_id` and requires a DELIVERY dropoff. The revised classify-at-PICKUP → choose RACK_A–D flow cannot be created through that API without a compatible data-contract change and a validated class-to-rack policy. Mock lifecycle tests use explicitly preassigned LINE Task fixtures. This is a functional blocker for the full V1 workflow, not a silently completed feature.
